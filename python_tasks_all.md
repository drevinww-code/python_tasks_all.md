## Блок 1. Простые задачи (разогрев)

### Простая задача 1: Своя версия `range`
**Тема:** Core, циклы, функции  
**Что сделать:**  
Напиши функцию `my_range(start, stop=None, step=1)`, которая возвращает `list` чисел, как обычный `range`.

**Ограничения:**
- Можно использовать только `while` (без `range` и генераторов).
- Поддержать формы вызова: `my_range(5)`, `my_range(2, 8)`, `my_range(10, 2, -2)`.
- При `step == 0` бросать `ValueError`.

**Проверка:**
- 10-15 тестов на базовые кейсы и границы.

### Простая задача 2: Безопасное деление
**Тема:** Core, исключения  
**Что сделать:**

**Ограничения:**
- Нельзя использовать `if b == 0`.
- Обработать только `ZeroDivisionError`, другие ошибки не глотать.

**Проверка:**
- Тесты на int/float и на неверные типы.

## Блок 2. Душные задачи (углубление)

### Душная задача 1: Мини-итерируемая коллекция без списка
**Тема:** Core, итераторы, протокол объектов  
**Что сделать:**  
Реализуй класс `RangeLike(start, stop, step=1)`, совместимый с `for`, `in`, `len`, `reversed`.

**Ограничения:**
- Нельзя хранить все значения в `list`/`tuple`.
- Нельзя использовать встроенный `range` внутри реализации.
- `in` должен работать за `O(1)` по времени (математика, не перебор).
- Должны корректно обрабатываться отрицательные `step`.
- При `step == 0` бросай `ValueError`.

**Проверка:**
- Сравни поведение с `range` на 20+ кейсах, включая граничные.
- Добавь тест на память: большие диапазоны не должны приводить к заметному росту RAM.

### Душная задача 2: Контекст-менеджер транзакции словаря
**Тема:** Core, `with`, исключения  
**Что сделать:**  
Реализуй `atomic_dict(d: dict)`, который в блоке `with` позволяет менять словарь:
- если блок завершился успешно — изменения сохраняются;
- если было исключение — словарь полностью откатывается.

**Ограничения:**
- Нельзя использовать `copy.deepcopy`.
- Нельзя пересоздавать внешний объект словаря (`id(d)` должен остаться тем же).
- Должен поддерживаться вложенный `with atomic_dict(d)`.

**Проверка:**
- Покрой тестами сценарии commit/rollback и вложенные транзакции.
- Проверь, что исключения не подавляются без явной причины.

---

### Душная задача 3: Стабильный LRU-кэш без `functools.lru_cache`
**Тема:** Core, структуры данных, декораторы  
**Что сделать:**  
Напиши декоратор `@lru(maxsize=128)`.

**Ограничения:**
- Нельзя использовать `functools.lru_cache`.
- Асимптотика `get/put` — `O(1)`.
- Ключ должен учитывать и `args`, и `kwargs` (порядок `kwargs` не влияет).
- Для нехешируемых аргументов должно быть понятное исключение.
- Должны быть методы `cache_info()` и `cache_clear()`.

**Проверка:**
- Тесты на hit/miss, вытеснение, корректность с kwargs, поток вызовов.

---

### Душная задача 4: Валидируемая модель через дескрипторы
**Тема:** OOP, дескрипторы  
**Что сделать:**  
Создай систему дескрипторов `IntField`, `StrField`, `ChoiceField`, и класс `User`.

**Ограничения:**
- Нельзя использовать `dataclasses`, `pydantic`, `attrs`.
- Валидация должна происходить в момент присваивания.
- Ошибки — информативные `TypeError/ValueError`.
- Значения хранятся на экземпляре, а не в дескрипторе (иначе утечки между объектами).

**Проверка:**
- Тесты на успешные и ошибочные присваивания.
- Проверка, что два экземпляра `User` не делят состояние полей.

### Душная задача 5: Кооперативное множественное наследование
**Тема:** OOP, MRO, `super()`  
**Что сделать:**  
Построй иерархию из 4-5 классов (включая "ромб"), где каждый `__init__`:
1) принимает часть параметров,  
2) валидирует их,  
3) передает остаток через `super().__init__(**kwargs)`.

**Ограничения:**
- Ни один `__init__` не должен вызываться дважды.
- Нельзя напрямую вызывать `Base.__init__(self, ...)`.
- Добавь инструментальный лог порядка вызовов.

**Проверка:**
- Тесты на порядок MRO и единичность инициализации.
- Кейс с ошибочным параметром должен падать в "правильном" классе.

### Душная задача 6: Неизменяемый хешируемый объект с корректной семантикой
**Тема:** OOP, `__eq__`, `__hash__`, иммутабельность  
**Что сделать:**  
Реализуй класс `Point3D(x, y, z)` как логически неизменяемый объект.

**Ограничения:**
- После создания изменение координат запрещено.
- `Point3D` должен быть пригоден как ключ `dict`/элемент `set`.
- Равенство только с объектами того же класса (не с tuple).
- Нельзя использовать `@dataclass(frozen=True)`.

**Проверка:**
- Тесты на hash-consistency, set/dict-поведение, запрет мутации.

### Душная задача 8: Анализ байткода функции

**Что сделать:**

**Ограничения:**
- Используй только стандартные модули (`dis`, `ast`, `inspect`, `types`).
- Для каждой функции поясни минимум 5 ключевых инструкций байткода.
- Сравни две версии одной логики (цикл vs comprehension).

**Проверка:**

### Душная задача 9: Песочница для `eval/exec` (и почему это почти безнадежно)
**Тема:** Интерпретация, безопасность  
**Что сделать:**  
Сделай "ограниченный" раннер выражений.

**Ограничения:**
- Запрещены `__import__`, `open`, `exec`, `eval`, доступ к `__builtins__` напрямую.
- Разрешены только арифметика, сравнения, булева логика и вызовы whitelist-функций.
- До выполнения выражение должно проверяться через `ast`.

**Проверка:**
- Набор из 20 "вредных" payload'ов, которые должны блокироваться.
- Набор из 20 валидных выражений, которые должны выполняться.
- Отдельный раздел: "какие атаки все еще потенциально возможны".

### Душная задача 12: Мини-фреймворк плагинов через ABC + динамический импорт
**Тема:** OOP + импорт + интерпретация  
**Что сделать:**  
Реализуй систему плагинов:
- базовый интерфейс через `ABC`;
- автопоиск модулей-плагинов в папке;
- проверка, что найденный класс реализует интерфейс.

**Ограничения:**
- Нельзя использовать готовые plugin-framework библиотеки.
- Ошибочный плагин не должен "ронять" всю систему (логируй и пропускай).
- Плагины должны загружаться лениво (по требованию).

**Проверка:**
- Минимум 3 валидных и 2 невалидных плагина.
- Юнит-тесты на discovery, валидацию и graceful degradation.

## Формат сдачи (чтобы было по-настоящему душно)

Для каждого задания:
1. `README` с архитектурой и обоснованием решений.  
2. Тесты (`unittest` или `pytest`) с покрытием граничных кейсов.  
3. Отдельный раздел "Какие компромиссы и почему".  
4. Раздел "Что сломается при масштабировании".  
5. Мини-ретро: "что сделал(а) бы иначе во второй итерации".

Если хочешь усложнить еще сильнее — добавь ограничение "не более N строк на решение" и "запрет на отдельные встроенные функции" для каждого задания.
